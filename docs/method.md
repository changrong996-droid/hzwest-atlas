# 活图纸方法书（初稿）

起草：hark-cs　日期：2026-11-08　状态：初稿，交 hark-cr 审定
依据：两轮「第二工程」试做（约 90 m² 三室两厅全屋装修）。第一轮由一个智能体轮流扮演三个分图（约 18 分钟）；第二轮由三家不同厂家的智能体真的并行干活（46 分钟）。文中「第一轮」「第二轮」都指这两次试做。

> 读法：每条规则后面跟着「为什么」，写的是试做里真撞上的事。规则可以改，但改之前先看看它是被哪件事逼出来的。

---

## 1. 这是什么、什么时候用

活图纸就是让一份工程数据同时长出三维、平面、横道图和建成后的样子，点哪里都能互相对上。这本方法书讲的是：**换一个新工程时，一个集成人怎么带几个分图智能体，在几十分钟到几天里把这样一页做出来。** 集成人负责定规则、派单、审查、退回、合并和测试；分图智能体各画一张图，只交自己的文件。工程大小不是重点（一套房子和一个车站用的是同一套办法），真正费工夫的是多人协作，所以本书大部分篇幅在讲「怎么分、怎么交、怎么验」。适用条件：已经有一份能推出工序和工期的数据（或者能先做出来），并且至少有两张图要互相联动。只画一张图，不需要这套。

## 2. 开工前（集成人做，约 10–15 分钟）

### 2.1 先把「通用层」搬过来，别从旧工程的页面里裁

通用层只有三块：**排程引擎**（规则推顺序、按班组排日期、关键链、自查）、**联动小函数**（图纸缩放平移、点中判断、三维盒子拾取、`#focus=` 读写）和**联动检查脚本**。这三块原样拷，剩下的页面骨架（宿主）按新工程重写。

为什么：第一轮实测，排程引擎 626 行一字没改就排出了装修工期（入住第 59 天，和公开资料的 54–64 天对得上）；联动小函数 38 行只改了 1 处。而原页面文件其余约 980 行里，直接写死杭州西站数据的地方约 160 处（塔吊、千斤顶镜头、地铁层、屋盖高度……），裁它比重写还慢。重写成新宿主只用了约 180 行、2 分钟多。

### 2.2 简报里先写死坐标和单位

原点在哪、哪个方向是 x、哪个方向是 z、平面图北在上还是南在上、长度用米还是毫米。写在接口之前。

为什么：分图之间唯一的共同语言就是坐标和编号。第二轮 B 画的厨房东墙立面「左北右南」没画反，是因为简报里写了；没写的地方（见 2.4）就各猜各的。

### 2.3 数据先交、图后画

谁负责「大家都要用的数据」（工序表、户型、点位表），谁就第一个交，集成人先合进主线，别人再在真数据上跑。别人可以先对着接口写，但要预期等一下，并且**数据合进主线后，集成人要通知下游拉主线重跑一遍检查。**

为什么：第二轮 B（立面图）开工时 A 的点位数据还不在主线上，任务书让它「对着接口写、用假数据自测、不要等」，它照做了，零等待——但 A 的数据 08:31 就进了主线，B 一直没去拉，**交付时从没在真数据上跑过**。两家的东西第一次拼在一起，是集成人合并时跑的那遍检查。这次碰巧一次过，下次不一定。

### 2.4 任务书里一次写全所有接口字段

图纸插件能拿到的每个字段都列成一张表，并写一句「没写在这里的字段不存在，不要假设」。尤其要写清：**画布宽高从哪拿**（`ctx.w`、`ctx.h`）、当前选中的是谁、放大倍数、主数字和标题栏的固定位置。

为什么：第一轮的插件接口里，「可点清单」函数拿不到画布大小——原仓库的屋面图是偷偷缓存上一次画图的尺寸绕过去的，这条暗规矩没写进文档。结果 B 发现了、提了请求；C 没发现，默认画布是 560×420。页面上点横道第 5 行，选中的是第 4 行。第二轮把字段表写全后，三家都从 `ctx.w / ctx.h` 取，这个老问题没再出现。

### 2.5 规则写完自己算一遍，确认能同时满足

每写一条「看起来怎样」的规则，就拿数字算：数据量 × 最小字号能不能装进最小的那块画布；两条规则会不会打架。打架时写清以哪条为准。

为什么：第一轮任务书写「横道图每个活动一行」，简报写「文字不小于 11 像素」。90 m² 装修也有 38 个活动，一屏挤下去字号只剩约 9 像素。C 照任务书做，被集成人按简报退回两次——锅在写规则的人。第二轮开工前按最小画布（560×540）算了一遍，实测画布和预算只差 4 像素，规则成立。

### 2.6 关键词要下定义，例子要和文字对上

像「已出现」「未开始」「截到墙内」这类词，写进术语表，给出能用代码判断的定义（例：已出现 = 状态 ≥ 0）。写完例子，拿例子倒推一遍文字。

为什么：第二轮任务书写「已出现的点位做成可点项」。A 读成「工序已经开始」，B 读成「图上画出来了」，结果同一个插座在 A 的图上第 0 天点不到、在 B 的图上第 0 天就能点到。另一处，简报写「超出户型的部分截到墙内（东墙点 x 就是 10.08–10.2）」——截掉一半应是 10.14，往里挪才是 10.08，规则自己矛盾。

### 2.7 把边界情况写进规则

「第 0 天开工的活动，材料前 1 天进场」这种算出负数的情况，事先写明怎么处理。

为什么：第二轮 C 画资金曲线时撞上「拆墙第 0 天开工、材料要第 −1 天进场」，图上画不出来，只好自己把拆墙材料费设成 0。处理得合理，但这是规则的漏洞，不该靠分图去猜。

### 2.8 第 0 步：命令行体检（用新智能体或新工具时）

每家智能体先跑一个「建一个文件、跑一条命令、退出」的小任务，记下：怎么选模型、怎么判断成功失败、日志在哪、怎么看它正在干什么。

为什么：第二轮光摸清三家命令行怎么用就花了约 10 分钟。有一家选模型的参数帮助里根本没写，是从程序里翻出来的；另一家要先设两个变量才能看对话。这是一次性成本，记下来下次就省了。

## 3. 分工与派单

### 3.1 一图一人

一张图只有一个负责人，一个文件只有一个人改。共用文件（宿主、简报、规则、检查总表）只由集成人改。

为什么：第一轮三条分支合并时代码零冲突，冲突全出在「大家都要改的文件」（看板、日志）上。第二轮把看板拆成每人一张小表、中间隔几行，三次合并都自动合上。

### 3.2 所有人用同一份提示词模板，只换各自的单子

模板见附录（第 10 节）。名字、目录、图号、分支名用占位符替换，其余一字不改。返工时在模板后面加一段「退回后返工」说明。

为什么：第二轮三家拿到的是同一份模板，所以三家的理解差异可以直接归因到「规则写得含糊」或「这家的习惯」，而不是「每人听到的话不一样」。这让复盘变得可行。

### 3.3 不许翻别人的分支；需要的东西由集成人给全

分图只看主线（main），不 fetch、不读别人的分支；不打印带改动明细的大段记录（如 `git log -p`）、不打印第三方库和二进制文件。需要别人的数据或接口，就提请求，由集成人合进主线后再给。

为什么：第二轮规则只禁止「改」别人的文件，没禁止「看」。Gemini 那家开工 15 分钟自己的文件一行没写，一直在拉别人的分支、读同事的代码；还打出了一份 1.57 MB 的带改动记录（连 1.27 MB 的三维库都打了出来），直接撑爆了模型的每分钟配额，会话停掉。

### 3.4 只提交自己的文件：禁止 `git add -A`、`git add .` 和 `git commit -a`

提交时一律 `git add <具体文件路径>`。集成人审查时第一眼看「改了哪些文件」，名单外的一律退回。

为什么：第一轮集成人的时间日志放在仓库里没提交，两次被分图「全部提交」顺手带进了他们的分支，越出了文件范围。第二轮写进规则后，这类事 0 次。

### 3.5 日志不进仓库

集成人的时间日志、截图、临时输出放在仓库外（或写进忽略清单），只当记事本。看板（认领表）一事一行、每行带固定编号，状态尽量由集成人统一改。

为什么：同上，第一轮日志被带走两次；集成人用脚本往看板写退回记录时，还因为两张表的分隔行长得像，插错了表。

## 4. 遇到歧义必须提问，集成人限时回复

### 4.1 规则

- 凡是规则文档里没写、需要自己做假设的地方，**都必须**在看板「接口请求」栏末尾追加一行（编号 Q-n，写清问题和自己打算怎么做）。只在最后的汇报里列假设，**不算数**，按交付不完整退回。
- 写完请求可以继续做不受影响的部分；受影响的部分先按最保守的理解做，并在提交说明里写「已提请求 Q-n」。
- 集成人**限时回复**：并行干活期间，每 10 分钟扫一次请求栏；每次审查前先看这一栏，再看代码。答复改变了规则的，同时改简报或任务书，并通知所有相关的人。

### 4.2 为什么

第二轮的模板里写的是：「看不懂就写一行请求，然后按你认为最保守的理解继续做完，不要停下来等回复。」本意是「问了也别干等」，实际效果却成了**「不用问」**：三家各自撞上了一处真的规则漏洞（「已出现」两种读法、「截到墙内」自相矛盾、第 −1 天进场），**一行请求都没写**，假设全写在最后的汇报里（A 列 2 条，B 列 4 条，C 列 2 条）。等集成人看到汇报，代码已经交了，只能退回重做。教训：「可以继续」和「必须先问」要同时写，而且要有人按时回。

## 5. 验收分三层

### 5.1 三层

| 层 | 谁做 | 查什么 | 例子 |
|---|---|---|---|
| ① 脚本检查 | 分图自己 + 集成人合并后再跑 | 不报错、字号范围、主数字恰好一个且在规定位置、点中区域够大且不互相压、编号前缀合法、没碰页面元素 | 第二轮通用检查每次把每张图画 126 遍 |
| ② 真开页面测试 | 集成人 | 用无头浏览器打开页面：点平面 → 三维框住；拖时间轴 → 数字、三维、图纸、链接同步；`#focus=` 链接直达；切图选中保留；零报错；两档窗口一屏放下 | 第一轮横道「点第 5 行选中第 4 行」是这一层抓到的，脚本一个没抓到 |
| ③ 汇报逐句对画面 | 集成人 | 把分图汇报里的每一句话，对着截图和相关的几行代码核一遍 | 第二轮 A 的汇报写「按四种状态配色」，代码第 40 行却是「未开始的点位直接跳过不画」；第 5 天整屋只看得到几个点。脚本和页面测试都过了，是读代码才发现的 |

### 5.2 能变成检查的，就别靠眼睛

第三层发现的问题，修的时候顺手加一条脚本检查。例如 A 返工时加了「第 0 天画出的虚线符号数 = 点位总数」；B 返工时加了「第 0 天没有可点的点位、最后一天全部可点」。

为什么：第三层贵（要人看、要读代码），而且会漏。第二轮 A 的问题 08:32 就能看出来，集成人当时只看了检查结果和一张截图，08:54 读代码才发现；A 改只用了 42 秒，前面 23 分钟都在等审查。

### 5.3 命令行报的成功或失败不可信，以仓库里的提交为准

判断一单做没做完，只看：分支上有没有新提交、看板那一行是不是「待审」、合并后检查过不过。不看智能体进程的退出码、结果状态字段或界面上的「进行中」。

为什么：第二轮 Claude 那家的最终结果标着 `status: ERROR / stream was interrupted`，活其实全做完、汇报也完整；Gemini 那家界面上一直显示「正在实现 f001.js」，其实已经停了 5 分钟。

## 6. 心跳与卡死

### 6.1 规则

- 分图每 **10 分钟**至少推一次进度提交（哪怕只是看板状态或半成品，只要检查能过）。
- 集成人按提交时间判断：**超过 15 分钟没有新提交，就当它停了**，先去查它的日志，确认原因后再发「继续」消息（同模板 + 一句说明中断原因和要避开的操作）。
- 同一家模型的多个会话（包括委托人自己在用的）共用每分钟额度。重活错开跑；派单前看一眼这家是不是正忙。

### 6.2 为什么

第二轮 Gemini 那家 08:41 因为撑爆配额（每分钟输入上限）停掉，**命令行、对话记录、任务状态都没报错**，界面仍显示「进行中」。集成人约 5 分钟后才起疑，又花约 4 分钟翻日志才找到「额度超限」那一行，08:46 发「继续」后它约 6 分钟就交了。同一份日志里还有委托人自己另外 3 个会话撞过同一个上限——额度是整台机器共用的。如果当时有「10 分钟一推」，停掉的事 10 分钟内就能从仓库看出来。

## 7. 退回

### 7.1 规则

- 退回写进看板「退回记录」（只有集成人写）：**改什么、为什么、以哪条规则为准**（写出规则所在文件和条目）。
- 返工提示 = 原模板 + 一段「退回后返工」：先合并主线、读那条退回记录、只按那条改。
- **每单最多退回两次。** 第三次想退回之前，先停下来查规则本身：是不是规则含糊、打架或漏了边界。是规则的问题就改规则（并通知所有人），不再让分图来回改；剩下的小毛病写进报告。

### 7.2 为什么

第一轮 C 的横道图被退回两次，根子是集成人写的两条规则打架（见 2.5），再退第三次也只是让分图在两条矛盾的规则之间换个方向猜。第二轮两次退回，一次是规则用词含糊（「已出现」），一次是交付和汇报对不上——前者本质也是规则的问题。退回写得清楚时，返工很快：B 返工改 18 行用了 3 分 18 秒，A 返工用了 42 秒。

## 8. 选什么智能体

| 智能体（第二轮用的工具） | 一句话特点 | 例子 |
|---|---|---|
| Claude Sonnet 5.5（agy） | 最快最省，适合当「数据枢纽」先交；但汇报要逐句核对 | 启动 1 分钟就推了第一次，4 分 21 秒交待审，返工 42 秒；可汇报两处和实物不符（「四种颜色」实际没画未开始；范围写 10.08 实际是 10.14） |
| DeepSeek 4.1 flash（dim） | 慢一些、啰嗦，但守规矩、汇报老实，适合中等难度、要跟着别人数据走的图 | 交付用约 11 分钟，输出里大段中文推理；主动列了 4 条假设；返工时自己注意到「开始时间」不该被覆盖，改回原值、把返工时间写进备注，比规则要求还细 |
| Gemini 4（Traycer） | 判断好、处理边界情况有分寸，但爱翻别人的东西、容易撑爆额度，且停了不报错 | 遇到「第 −1 天进场」自己定了合理做法并写明理由；但开工 15 分钟一行没写，打出 1.57 MB 记录撑爆配额后静默停掉 |

用法建议：数据和接口给最快的那家先交；依赖别人数据的图给守规矩的那家；独立、需要判断的图给判断好的那家，并在提示里加一句「不看别人分支、不打印大段补丁」。三家都不报（或不全报）用量，成本只能看时间。

## 10. 附：给分图智能体的提示词模板

取自第二轮实际使用的模板，去掉了机器路径和账号，并按本书第 3–6 节补了四处（标「新增」）。花括号里的占位符由集成人替换：`{名字}` 分图代号，`{目录}` 它的工作目录，`{图号}` `{图名}` 它的单子，`{集成人}` 集成人代号，`{检查命令}` 本工程的检查总表命令。

```text
你是 {名字}，在一个多方协作的小项目里负责一张图纸。另外几位同事是别家公司的智能体，正和你同时在各自的目录里干活；你们只通过 git 仓库协作，集成人 {集成人} 负责审查、退回和合并。

工作目录：{目录}（已是共享仓库的克隆，当前在 main）。
你的单子：{图号} {图名}；任务书 docs/tasks/{图号}.md；分支 agent/{名字}/{图号}。

按顺序做：
1. 先完整读 AGENTS.md、BRIEF.md、docs/tasks/{图号}.md，再动手。需要参考写法可以看任务书里点名的示例文件（只读）。
2. git checkout -b agent/{名字}/{图号}；把 CLAIMS.md 里你那一行的状态改成「进行」，「开始」填 `date` 命令的输出；只 `git add CLAIMS.md`，提交标题 "[claims] {图号} 进行"，然后 git push origin agent/{名字}/{图号}。
3. 按任务书写代码。只许改 AGENTS.md 名册里你那一栏白名单里的文件；不许改别人的文件，不许改共用文件（简报、规则、检查总表、宿主页面等）。
4. 提交时只用 `git add <具体文件路径>`；禁止 `git add -A`、`git add .`、`git commit -a`。提交标题 "[{图号}] 中文说明"，提交信息最后一行写 "Agent: {名字}"。
5. 每次推送前跑 `{检查命令}`，必须打印 OK；不 OK 就自己修到 OK。
6.（新增）至少每 10 分钟推一次进度提交（能过检查的半成品也行）。
7. 做完：把 CLAIMS.md 你那一行状态改成「待审」，「待审时间」填 `date` 的输出，提交并推送你的分支。不要合并到 main，不要推 main，不要强推。
8.（改）凡是规则里没写、需要你自己做假设的地方，都必须先在 CLAIMS.md「接口请求」表末尾追加一行（编号 Q-<下一个数字>，写清问题和你打算怎么做），再继续。不受影响的部分照常做；受影响的部分按最保守的理解做，并在提交说明里写「已提请求 Q-n」。只写在最后汇报里的假设不算数，会被退回。集成人每 10 分钟看一次请求栏。
9.（新增）只看 main，不 fetch、不读别人的分支；需要别人的东西就提请求。不要打印带补丁的 git log、第三方库或二进制文件的内容。
10. 不装依赖，不访问外网，不启动服务器或常驻进程，不动 {目录} 以外的任何目录（共享仓库只通过 git push 访问）。
11.（新增）汇报里说的每一句「画了什么、什么颜色、什么范围」，都要对照你自己的代码写，别照抄任务书里的例子。

最后用中文简短汇报：做了什么、检查结果、推了哪几个提交、提了哪些请求。
```

【这是退回后的返工】你的分支 agent/{名字}/{图号} 已被集成人退回 {n} 次。先在你的分支上 `git fetch origin && git merge origin/main`，再读 CLAIMS.md「退回记录」里写给你的那一条，只按那条改；第 2 步改成：把你那一行状态改回「进行」再动手（不用新建分支）。做完照第 7 步改「待审」推送。

## 附：集成人一页清单

7. 数据单合并后通知下游拉 main 重测（2.3）。
8. 退回写清依据；同一单第三次之前先查规则（7.1）。
9. 收尾：把计时、退回原因、规则改动回写本书。
